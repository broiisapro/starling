## Goal
Starling is a concurrency machine: parallel worktrees, a serial merge queue, a shared SQLite store, a flock registry with heartbeats, an engine that can be cancelled mid-merge, and dashboards reconnecting over SSE. Races don't show up in happy-path tests, but they do on stage. Probe for them with deterministic interleavings: fakes with gates (`deferred` promises you release in a chosen order) instead of sleeps, plus a few small real-git and real-SQLite bursts. Great looks like ~45 probes, a reusable interleaving toolkit, and every race reported with a deterministic replay.

## Deliverables
1. **Toolkit `interleave.ts`.** `deferred<T>()`; `Gate` (`await gate.at('merge:start')` inside fakes, `gate.release('merge:start')` from the test); `permutations(steps)` for ≤ 5 steps (≤ 120 orders); `runSchedule(order, steps)` running async steps in a given release order; `maxConcurrency()` instrumentation (`enter()/exit()` counters); `countingBus(bus)` wrapping `createEventBus()` to count live subscribers. Unit-test the toolkit itself (~5 tests).
2. **`locks.test.ts` (~7).** Workspace `KeyedMutex`: same key strictly serial, different keys concurrent, a throwing critical section releases the lock, `pending(key)` and `keys()` accurate under load; `Semaphore`: never more than `limit` active (instrumented), FIFO order, rejection frees the slot; `boundedExec(exec, n)` caps concurrent exec calls.
3. **`merge-queue.test.ts` (~7).** `createMergeQueue` with a gated fake merge: 20 concurrent `enqueue`s → max concurrency 1 per repo+branch and results in enqueue order for every permutation of release timing; enqueue while a merge runs; a merge that rejects mid-chain; two integration branches overlap (concurrency 2); `pending()` consistent at every gate. Real repo (one test): two concurrent `createMerger().merge()` calls on the same integration branch **without** the queue (Epic 70 F1): pin what happens (integration sha, both results) and todo if one merge is lost or the worktree is left dirty.
4. **`workspace-burst.test.ts` (~6, real git, ≤ 8 parallel).** 8 concurrent `create()` on one repo all succeed (lock contention retried, `isLockContention`), distinct paths; concurrent `commitAll` in different worktrees; `remove()` of the same path twice concurrently doesn't throw; `create` and `remove` of the same branch interleaved; `predictConflicts` while another worktree commits leaves no stray refs; `ensureIntegrationBranch` called concurrently from two "runs" ends with one branch at one sha.
5. **`store.test.ts` (~5).** Two `createSqliteStore(file)` instances writing 2,000 events each concurrently (WAL + `busy_timeout`) → no lost or duplicated events; `saveRun` from two instances (last writer wins, never a torn JSON row); `attachRecorder` with a burst of 10,000 synchronous `publish`es → all persisted in order; reading `events(id, since)` while writing returns a consistent prefix.
6. **`flock.test.ts` (~6).** `createFlockHub` + `createRegistry`: 10 concurrent `register` calls with the same url → one node id and one `joined` event; `heartbeat` racing `sweep()` at exactly `offlineAfterMs` (no left-then-stats zombie); `remove` during an `onChange` dispatch; a listener that unsubscribes others mid-dispatch; two `bundle(ref)` racing `setActiveRepo(other)`.
7. **`engine.test.ts` (~8).** Engine with core fakes and gates (copy a minimal harness: `createEngine` + `MockNode`/`MockAuditor`/`MockMerger` subclasses that await gates): `cancel` while a task is `merging` → the task ends `cancelled` **or** `merged`, never both, and `run.finished` is published exactly once; `cancel` twice concurrently; `abortTask` while `auditing`; node `simulateDeath()` during `collect`; `waitForFinish` called before `start` resolves and after `run.finished`; two runs started concurrently on the same repo keep separate task maps; `maxParallel: 2` with 6 ready tasks and gates released in all orders never exceeds 2 active (Epic 70 F2 slot reuse before cleanup: pin as known).
8. **`sse.test.ts` (~5).** Against `startServer({ port: 0, hostname: '127.0.0.1' })` with a `countingBus`: 30 sequential connect/abort cycles leave subscribers at baseline; 10 concurrent clients with `?since=` while events are published during backlog writing: each client sees every event exactly once; `stop()` with open streams resolves and leaves zero subscribers. (Web client reconnect storms belong to Epic 191.)
