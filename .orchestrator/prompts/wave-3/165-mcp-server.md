## Goal
With an MCP server, any agent (Claude Code, opencode, Cursor) can drive Starling as a tool: "plan this goal with Starling", "how is run X doing?", "give me the report", and read the live event stream as a resource. It's a strong judge story ("our harness is itself a tool for other agents") and it has to be dependency-free: a hand-rolled JSON-RPC 2.0 server over newline-delimited stdio, tested entirely over in-memory streams. Great looks like: `claude mcp add starling -- bun /path/to/integrations/mcp/main.ts` works, `tools/list` shows three well-described tools, and reading `starling://runs/<id>/events` returns the run's events as NDJSON.

## Deliverables
1. **JSON-RPC core** `integrations/mcp/jsonrpc.ts`: types for request, notification, response and error; `parseMessage(line): Parsed | RpcError` (-32700 parse error, -32600 invalid request); standard codes -32601, -32602, -32603; requests answered in completion order, notifications never answered; batches (arrays) rejected with -32600 (MCP 2025-06-18 removed batching).
2. **Stdio transport** `transport.ts`: `serveLines(input: ReadableStream<Uint8Array>, output: { write(s: string): void }, handle: (msg) => Promise<object | undefined>): Promise<void>`: newline-delimited UTF-8, partial chunks and multi-byte characters split across chunks handled, blank lines ignored, a line limit (1 MiB → error, not a crash). Logs go to stderr only; **stdout carries protocol frames only**.
3. **MCP server** `server.ts`: `createMcpServer({ backend: StarlingBackend, name?: string, version?: string, clock?, log? })` → `{ handle(msg): Promise<object | undefined>; close(): void }`. Methods: `initialize` (negotiate `protocolVersion` from `['2025-06-18', '2025-03-26', '2024-11-05']`, echoing the client's when supported, otherwise the latest; capabilities `{ tools: { listChanged: false }, resources: { subscribe: true, listChanged: false } }`; `serverInfo`; short `instructions`), `notifications/initialized`, `ping`, `tools/list`, `tools/call`, `resources/list`, `resources/templates/list`, `resources/read`, `resources/subscribe`, `resources/unsubscribe`, `notifications/cancelled`. A request before `initialize` gets an error.
4. **Tools** (hand-written JSON Schemas, results as `content: [{ type: 'text', text }]` plus `structuredContent`; tool failures are `isError: true` results, not protocol errors): `starling_plan { goal: string; repoPath?: string }` → plan summary and task table text, structured `{ plan, issues }`; `starling_status { runId?: string }` → newest or given run with per-status counts and in-flight tasks; `starling_report { runId?: string; file?: string; format?: 'md' | 'json' }` → flight report. Descriptions tell an agent when to use each one (no run starting from MCP in this epic: planning is read-only and safe).
5. **Resources:** `starling://runs` (JSON list of runs), `starling://runs/{runId}` (the `Run`), `starling://runs/{runId}/events` (NDJSON, `mimeType: 'application/x-ndjson'`, optional `?since=<ts>` and the last 500 events by default), with the matching templates. `resources/subscribe` on an events URI follows the run's SSE and sends `notifications/resources/updated` at most once per second (coalesced); unsubscribe and `close()` stop the stream.
6. **Backend port** `backend.ts`: `interface StarlingBackend { plan(i): Promise<{ plan: Plan; issues: PlanIssue[] }>; listRuns(): Promise<Run[]>; getRun(id?): Promise<Run | undefined>; events(runId, o: { since?: number; limit?: number }): Promise<StarlingEvent[]>; follow(runId, onEvent, signal): Promise<void>; report(i): Promise<string> }`. Implementations: `createHttpBackend({ baseUrl, token?, fetch, idleMs = 200 })` (reads `/api/runs*`; reads events from the SSE backlog and stops after `idleMs` with no frame or at `limit`; `report` tries `GET /api/runs/:id/report` (Epic 111) then a local summary); `createCliBackend({ run: (argv) => Promise<{ code; stdout; stderr }>, cli })` for `plan` (`starling plan <goal> --repo <p> --json`, validated with `PlanSchema`/`PlanIssueSchema`) and for `--file` reports; and a composite default that uses HTTP when `/api/health` answers and the CLI otherwise.
7. **Entry** `main.ts`: reads `STARLING_SERVER_URL`, `STARLING_TOKEN`, `STARLING_BIN`; wires stdin/stdout; exits cleanly on stdin EOF and SIGTERM.
8. **README.md:** set-up snippets for Claude Code (`claude mcp add starling -- bun <abs>/integrations/mcp/main.ts`), opencode (`opencode.json` `mcp` block with `type: 'local'` and a `command` array) and a generic client, the tool and resource list, and a transcript of a session (initialize → tools/list → tools/call).
9. **Tests over in-memory streams only** (a `ReadableStream` fed by the test and a capturing writer; a fake backend; a fake `fetch` that serves `fixtures/runs/sky-todo-launch-day.jsonl` as SSE): the full handshake, version negotiation, every error code, notifications unanswered, split-chunk framing, unicode, the oversized line, each tool's success and `isError` paths, resource list/read/templates, subscribe → coalesced update → unsubscribe, the CLI backend's argv and JSON validation, and one test spawning `bun integrations/mcp/main.ts` with a stub backend env that does initialize → tools/list over real pipes (≤ 1 s).
