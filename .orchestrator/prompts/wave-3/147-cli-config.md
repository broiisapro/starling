## Goal
`starling init` writes a nicely commented `starling.config.yaml`; after that, people edit it by hand and get zod errors. `starling config` makes the config a first-class, safe thing: read any key with its effective value and where it came from, change a key **without destroying the comments** `init` wrote, validate with friendly messages (including typo detection, because the schema silently strips unknown keys), and show which file is in play. Great looks like: `starling config set maxParallel 12` keeps every comment and alignment, `starling config validate` says "`maxParalel` is not a Starling setting: did you mean `maxParallel`?", and nothing ever writes an invalid file.

## Deliverables
1. `index.ts` exporting `extension` (`name: 'config'`) registering `starling config` with subcommands `get <key>`, `set <key> <value>`, `unset <key>`, `list`, `validate`, `path`, and shared options `--file <path>` (explicit config file) and `--repo <dir>` (where to look, default cwd). `get`/`list` take `--json`; `list` takes `--defaults` (show every key incl. defaults) and `--changed` (only keys that differ from defaults).
2. Keys are dot paths over `StarlingConfigSchema` from core (`maxParallel`, `flock.hubMaxSessions`, `models.worker.model`, `providers.deepseek.baseUrl`, `budget.maxUsd`). `schema-paths.ts` walks the zod 4 schema (unwrap defaults/optionals; objects, enums, numbers, booleans, strings, nullable, records) and returns `{ path, type, enumValues?, default }[]`, so help and errors can list valid keys and expected types. Record keys (`providers.<name>`) accept any name.
3. `get`: prints the effective value (`loadConfig(file, repo)`), plus its source (`file` or `default`) in dim text; `--json` prints the raw JSON value. An unknown key → exit 2 with up to 3 "did you mean" suggestions (Levenshtein ≤ 3 over all paths).
4. `set`: coerce the string by the target type (int/number/boolean/null/enum/string; `"8"` → `8`, `true/false`, `null` only where nullable), validate the **whole resulting config** with `StarlingConfigSchema.safeParse` over the deep-merged raw document before writing, and print `maxParallel: 8 → 12`. Refuse keys that look like secrets (`apiKey`, `token`, `password`) with the hint to use `providers.<x>.apiKeyEnv` and an env var. No config file yet → create `starling.config.yaml` in `--repo` containing a short header comment and only the key being set.
5. `yaml-edit.ts`: a small **comment-preserving** line editor (the `yaml` package isn't resolvable from `apps/cli`, and `Bun.YAML.stringify` drops comments). `setYamlPath(text, path, value): string` and `unsetYamlPath(text, path): string` handle: block mappings at any depth (replace only the scalar after `key:`, keeping the original spacing and the trailing `# comment`), flow mappings on one line like `github: { enabled: false, repo: null }   # comment` (rewrite that mapping with the key changed, keep the comment), adding a missing key under an existing block parent (with the parent's child indent), adding a missing parent block at the end of the file, and quoting strings only when YAML needs it. Verify every edit by re-parsing with `Bun.YAML.parse` and comparing to the intended object; if the line editor can't handle a shape, fall back to rewriting the file with `Bun.YAML.stringify` **only after** warning that comments will be lost and getting `--force`.
6. Writes are atomic (temp file in the same dir + `rename`) and keep a one-deep backup `starling.config.yaml.bak`.
7. `validate`: exit 0 when valid; otherwise exit 1 listing each zod issue as `path: message (expected <type>, got <value>)`. Also walk the raw YAML for **unknown keys** (the schema strips them silently) and print a warning with suggestions; `--strict` turns unknown keys into errors. Also warn when `flock.hubMaxSessions` < `maxParallel`, when a role uses a provider missing from `providers`, and when a provider's `apiKeyEnv` variable is unset in `env` (warning only).
8. `path`: prints the file `loadConfig` would read (first of `CONFIG_FILENAMES` in `--repo`), or `(none — defaults in use; starling init writes one)` with exit 0.
9. `list`: aligned `key = value` lines (or nested JSON with `--json`), `source` column, secrets never printed (there are none in the schema today; mask any key matching the secret rule anyway).
10. `try.ts`: `bun apps/cli/src/ext/config/try.ts get maxParallel --repo examples/sky-todo`.
11. Tests (≥ 40): the editor on a copy of `starling init`'s output format (copy a sample of `renderConfigYaml`'s output from `apps/cli/src/init.ts` into a fixture: comments, column-aligned trailing comments, flow mappings) and on `starling.config.example.yaml`: set top-level, nested block, inside flow mapping, add missing key, add missing parent, unset, string quoting (`'yes'`, `'#hash'`, `': colon'`), round trip equals intended object, comments preserved byte-for-byte on untouched lines; coercion per type and enum errors; invalid values never written; secret refusal; unknown-key suggestions; `validate --strict`; `path` with no file; atomic write leaves `.bak`.
