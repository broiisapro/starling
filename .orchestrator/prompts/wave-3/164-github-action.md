## Goal
"Label an issue `starling` and the flock replies with a plan" is the most shareable way to show Starling on GitHub. Build a composite action that (a) on an issue labelled `starling` by a trusted user turns the issue into a goal, runs `starling plan --json`, and posts or updates **one** comment with the task table, a Mermaid DAG and any lane warnings, and (b) given a run recording (`run.jsonl` artifact), posts a flight report. The pure parts (issue → goal, plan → comment, recording → report, comment upsert decision, trust check) are scripts with tests. The YAML is hardened against the classic Actions script-injection hole. Great looks like: the example workflow is copy-paste ready, and the rendered comment looks good enough to screenshot for the README.

## Deliverables
1. **Composite action** `integrations/github-action/action.yml`: inputs `mode` (`plan` | `report`), `github-token`, `repo-path` (default `.`), `run-file` (report mode), `llm-profile` (sets `STARLING_LLM_PROFILE`), `comment` (default `true`), `max-tasks`; outputs `comment-url`, `task-count`. Steps: `oven-sh/setup-bun@v2` pinned to bun `1.4.4`; `bun install --frozen-lockfile` in the Starling checkout the action ships in (`$GITHUB_ACTION_PATH/../..`, because `uses: <owner>/starling/integrations/github-action@<ref>` downloads the whole repo); then one `bun "$GITHUB_ACTION_PATH/scripts/<mode>.ts"` step.
2. **Script-injection hardening:** no `${{ … }}` expression inside any `run:` string. Every event value reaches scripts through `env:` (e.g. `ISSUE_TITLE: ${{ github.event.issue.title }}`) or the event payload file `$GITHUB_EVENT_PATH`. The script reads the issue from `GITHUB_EVENT_PATH` JSON, not from env, where possible.
3. **Trust gate (pure)** `scripts/trust.ts`: `isTrustedTrigger(event): { ok: boolean; reason: string }`: action `labeled`, label name `starling` (configurable), and `sender`/`issue.author_association` in `OWNER | MEMBER | COLLABORATOR`. Untrusted → exit 0 with a notice, never a plan (planning spends the repo's model budget).
4. **Issue → goal (pure)** `scripts/goal.ts`: `goalFromIssue({ title, body, number, url }): { goal: string; warnings: string[] }`: title plus body with HTML comments, images and `<details>` noise stripped; task-list items kept; capped at 4 000 chars with a note; empty → a friendly error comment.
5. **Plan → comment (pure)** `scripts/render-plan.ts`: `renderPlanComment(result: { plan: Plan; issues: PlanIssue[] }, ctx: { issueNumber, repo, runUrl? }): string`: headline (`🐦 Starling planned 7 tasks · 3 can fly at once`), a table (key, title, owns, depends on), a fenced `mermaid` `graph TD` of `dependsOn` (ids sanitised), lane issues as `> [!WARNING]` callouts, a collapsed `<details>` with each task's DoD, a footer with the marker `<!-- starling:plan issue=N -->` and a "how to run it" line. Clamp to GitHub's 65 536 chars (reuse `clampBody` from `packages/github/src/index.ts`). Validate input with core `PlanSchema`.
6. **Recording → report (pure)** `scripts/render-report.ts`: try `starling report <file> --format md` first (Epic 146 builds it in parallel; feature-detect "unknown command"); otherwise `summarizeRecording(events: StarlingEvent[]): RunSummary` + `renderReportComment(summary)`: outcome, tasks merged/failed/conflict, wall time, max birds in flight, cost and saved-vs-API from the last `metrics` event, per-node task counts, failed audits with their first fix instruction. Parse JSONL with `StarlingEventSchema`, skipping bad lines with a counted warning.
7. **Upsert (pure + thin IO)** `scripts/upsert.ts`: `decideComment(existing: Array<{ id: number; body: string; user: string }>, marker: string): { action: 'create' } | { action: 'update'; id: number }` (only update comments made by the bot user); IO through `gh api` with an argv array (`repos/{owner}/{repo}/issues/{n}/comments`, `--method PATCH` for updates), body sent via `--input -`/stdin, never on the command line.
8. **Failure UX:** when planning fails (no model configured, timeout, validator errors), post or update the same comment with a short, kind explanation and the next step (for example "set `llm-profile` and the provider secret"), and exit non-zero only for genuine errors.
9. **Examples** `integrations/github-action/examples/starling-plan.yml` (`on: issues: types: [labeled]`, `permissions: { issues: write, contents: read }`, concurrency per issue) and `examples/starling-report.yml` (`workflow_dispatch` with a run-file input and an `upload-artifact` step), plus `README.md` (setup, secrets, the trust model, a sample comment).
10. **Tests:** trust gate matrix, goal stripping and cap, plan comment (markers, Mermaid id sanitising, clamp, warning callouts) from `fixtures/plans/sky-todo-launch-day.json`, report from `fixtures/runs/sky-todo-launch-day.jsonl`, upsert decisions, and a **static YAML test** that parses `action.yml` and both examples with `Bun.YAML.parse` and asserts no `${{` inside any `run:` value, pinned bun version, and least-privilege `permissions`. At least 30 tests, under 3 s.
